# Bibliography Forensic Audit — Findings

Scope: `paper/main_fgcs.tex`, 81-entry manual `thebibliography`. Full methodology:
programmatic key cross-check (citation keys used in `\citep`/`\citet` vs. `\bibitem`
keys defined) plus manual DOI/URL inspection. No metadata was invented; gaps are
reported, not filled.

## Clean (no action needed)

- **Every cited key resolves to a defined bibliography entry, and vice versa.**
  81 unique keys used in text == 81 `\bibitem` entries defined. Zero cited-but-missing,
  zero defined-but-uncited.
- **Zero duplicate bibliography keys** (programmatic check).
- **Zero duplicate DOIs** across the 41 entries that carry one (programmatic check).
- Confirmed via a clean multi-pass `tectonic` build: zero `natbib` "Citation ... undefined"
  warnings, zero "Reference ... undefined" warnings.

## Real issue found (partially resolved)

- **Most web/software references lack an explicit "accessed [date]" annotation**,
  which FGCS's Guide for Authors requires as a minimum for web references ("as a
  minimum you should provide the full URL and the date when the reference was last
  accessed").

  **Resolved for 3 entries**, using a documented (not invented) date found in
  `paper/FGCS_AUDIT.md` §8.A: "This is public evidence of the architectural
  ingredient, gathered and verified by reading the actual issue pages ... on
  2026-09-23." This statement explicitly and unambiguously covers exactly these
  three sources, so "Accessed 23 September 2026." was added to each:
  - `litellm14457` (BerriAI, 2025)
  - `opengate1148` (Etalab, 2026)
  - `cliproxy2179` (Router-for-me, 2026)

  **Still unresolved (9 entries)** — a *different* audit file, `paper/ieee_reference_audit.md`
  (generated by `scripts/audit_references.py`, last committed 2026-08-19), records that
  these sources were checked via live GitHub REST API calls / HTTP 200 fetches, but
  contains no explicit "accessed on [date]" sentence the way the FGCS_AUDIT.md note
  does — only the file's own git commit date as an indirect upper bound. That's not
  precise or explicit enough to cite as a documented access date without inferring
  one, so none was added:
  - `llamacpp` (Gerganov et al., n.d.)
  - `kettle` (Kettle, 2023)
  - `aperture247` (Lightning Labs, 2026)
  - `cwe807` (MITRE, n.d.)
  - `tiktoken` (OpenAI, n.d.)
  - `owasp` (OWASP GenAI Security Project, 2025)
  - `newapi5235` (QuantumNous, 2026)
  - `sse` (WHATWG, n.d.)
  - `llmjacking` (Sysdig Threat Research Team, 2024) — no matching record found in
    either audit file at all.

  If you know the actual access date for any of these 9 (e.g. from your own memory
  of when you last checked them, or other records not in this repository), tell me
  the date and I'll add it. I will not infer or default to a commit date or today's
  date.

- **`n.d.` (no date) entries**: three sources cite `n.d.` (`llamacpp`, `cwe807`,
  `tiktoken`) — this is legitimate for living/undated web resources (a GitHub repo,
  a CWE registry entry, a documentation page) and is not itself an error, but FGCS's
  reference-style examples don't show this pattern explicitly. Low-severity; flagging
  for awareness only, not changing it (the content is accurate — these sources genuinely
  have no fixed publication date).

No other bibliography defects (malformed DOI, wrong journal name, retracted paper,
citation to a nonexistent work) were found.
